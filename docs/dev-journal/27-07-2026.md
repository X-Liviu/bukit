### Backend

#### API

- **US-02 implementada: manejo centralizado de errores y registro de sucesos.**
  - **Contrato de error compartido** en `packages/core` (`api-error.ts`): `apiErrorSchema` Zod con forma `{ error: { code, message, details? } }` — core es la única fuente de verdad y el futuro `api-client` consumirá el mismo esquema (RNF-03). Con su test unitario.
  - **`AppError`** (`errors.ts`): error de negocio con estado HTTP y código estable + fábricas (`badRequest`, `unauthorized`, `forbidden`, `notFound`). Las rutas **lanzan**, nunca responden errores por su cuenta.
  - **`logger.ts`**: pino con nivel por entorno (debug en dev con pino-pretty, info/JSON puro en prod, apagado en test para no ensuciar Vitest).
  - **`middleware/error-handler.ts`**: `notFoundHandler` (404 uniforme; el de serie de Express es HTML) + `errorHandler` final: `AppError` → su estado/código; `ZodError` → 400 `VALIDATION_ERROR` con detalle campo a campo; resto → 500 `INTERNAL_ERROR` genérico (el stack va al logger, jamás al cliente). Con guarda de `headersSent`.
  - **`app.ts` refactorizada a factoría `createApp(extraRoutes?)`**: pino-http → CORS/JSON → rutas → rutas inyectadas → 404 → errorHandler. _Alternativa descartada_: instancia única exportada (como hasta ahora); _porqué_: las pruebas necesitan inyectar rutas que fallan **antes** de los manejadores finales, y una instancia ya construida no lo permite sin reordenar la cadena.
  - **6 pruebas de integración** (Vitest + Supertest, sin BD): `/health`, 404 uniforme, error síncrono → 500 sin filtrar detalles, error **asíncrono** → 500 (comprobado: Express 5 lo propaga solo, sin `express-async-errors` — con Express 4 habría hecho falta), `AppError` de negocio, `ZodError` → 400 con detalle. Todas validan el cuerpo contra `apiErrorSchema` de core.
  - zod añadido a la API **con la misma versión exacta que core** (3.24.1): si divergieran, `instanceof ZodError` fallaría entre paquetes (dos clases distintas en el almacén de pnpm). Anotado como receta.
  - **Tras la revisión adversarial** (ver Problemas): rama nueva en el errorHandler para los errores del propio framework (body-parser: JSON malformado → 400, cuerpo >100 kb → 413, charset → 415, con código estable y mensaje propio), redacción en el logger (`authorization`, `cookie`, `set-cookie`, `err.body`), `X-Powered-By` deshabilitada, y 8 pruebas más (framework, details de AppError, niveles de registro con espías, guarda de `headersSent`, redacción). ## Problemas encontrados y cómo se resolvieron

- **La revisión adversarial previa al commit confirmó 9 hallazgos de 12 propuestos** (4 lentes en paralelo —correctitud, seguridad, pruebas, convenciones— y un verificador escéptico por hallazgo que intentó refutarlo reproduciéndolo en runtime). Los tres graves, todos verificados ejecutando la app real: (1) **los errores del propio framework se aplanaban a 500** — un JSON malformado del cliente respondía «error interno del servidor», violando la semántica HTTP y ensuciando el monitoreo con stacks a nivel error; ahora body-parser se traduce a 400/413/415 con código estable. (2) **pino-http registraba todas las cabeceras en claro** — en cuanto exista el JWT (US-05), cada petición habría volcado el token a los logs (suplantación + RGPD); redacción en el pino base. (3) **el SyntaxError del body-parser arrastra el cuerpo crudo en `err.body`** — un login con JSON truncado habría dejado la contraseña en el log; no se registra el `err` completo y el logger redacta `err.body` como red de seguridad. Menores: `X-Powered-By` delataba el framework, 2 huecos de cobertura (details de `AppError`, niveles de registro/`headersSent`) y 2 identificadores en español en tests. Los 3 rechazados cayeron con refutación razonada (p. ej. «la rama async sin cubrir» no existe como rama: ambos casos atraviesan el mismo código). **Evidencia de primera para la mitigación de R5**: nada generado se integra sin revisión y pruebas — y la revisión encontró defectos reales que la suite en verde no veía.
