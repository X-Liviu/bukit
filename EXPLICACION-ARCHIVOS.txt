## Raíz del monorepo (tooling y configuración)

Esta carpeta raíz no contiene código de la aplicación: solo archivos de configuración que gobiernan **todo** el monorepo a la vez (los tres `apps/` y los `packages/`). La idea de un monorepo es tener una única fuente de verdad para las herramientas (versiones, linter, formateo, TypeScript) en lugar de repetirlas en cada proyecto. A continuación, archivo por archivo.

---

### `package.json`

**Qué es.** El manifiesto raíz del monorepo (formato npm/pnpm). No describe una librería publicable, sino el "paraguas" que coordina todo.

**Para qué sirve.** Declara el gestor de paquetes, las versiones de Node/pnpm exigidas, las herramientas comunes (devDependencies) y los scripts que se ejecutan desde la raíz para operar sobre todos los subproyectos.

**Por qué cada decisión concreta:**
- `"private": true` — impide publicar este paquete por accidente en npm. La raíz de un monorepo nunca se publica; solo agrupa.
- `"version": "0.0.0"` y `"license": "UNLICENSED"` — es un TFG, no un producto distribuible; la versión es simbólica y la licencia bloquea uso externo.
- `"type": "module"` — activa ESM (usar `import`/`export`, no `require`). Es coherente con `eslint.config.mjs` y con el TypeScript configurado en modo ESNext.
- `"packageManager": "pnpm@9.15.0"` — fija el gestor y su versión exacta. Junto con `corepack enable`, garantiza que todo el mundo use **exactamente** ese pnpm sin instalarlo a mano.
- `"engines": { "node": ">=22", "pnpm": ">=9" }` — declara los mínimos. Combinado con `engine-strict=true` en `.npmrc`, el `install` avisa/falla si no se cumplen. Evita el clásico "en mi máquina funciona".
- `"volta": { "node": "22.11.0" }` — Volta es un gestor de versiones de Node; si lo tienes instalado, cambia automáticamente a esa versión exacta al entrar en la carpeta. Es una comodidad opcional (redundante con `.nvmrc`, pero más preciso).
- **Scripts.** Divididos en dos grupos:
  - Calidad de código: `lint`/`lint:fix` (ESLint sobre todo), `format`/`format:check` (Prettier), y `typecheck` que usa `pnpm -r typecheck` — la flag `-r` (recursive) lanza el script `typecheck` de **cada** paquete del workspace. Así se comprueban los tipos proyecto por proyecto.
  - Base de datos: `db:up`/`db:down`/`db:reset` levantan/paran/borran Postgres vía `docker compose` (el `-v` en reset borra también el volumen, es decir los datos). `db:migrate`/`db:studio`/`db:seed` usan `pnpm --filter @bukit/api ...` para ejecutar el comando **solo** en el paquete de la API (donde vive Prisma). `--filter` es la forma pnpm de apuntar a un subproyecto por su nombre.
- **devDependencies** — solo herramientas transversales, no dependencias de la app: el motor de ESLint 9 (`eslint`, `@eslint/js`), el puente TypeScript↔ESLint (`typescript-eslint`), `eslint-config-prettier` (apaga reglas de estilo que chocan con Prettier), `prettier`, `typescript`, `globals` (lista de variables globales conocidas como `process`) y `@types/node` (tipos de Node para TS).

### `pnpm-workspace.yaml`

**Qué es.** El archivo que le dice a pnpm que esto es un **workspace** (monorepo) y dónde están los subproyectos.

**Para qué sirve.** Sin él, pnpm trataría la carpeta como un único proyecto. Con él, pnpm descubre cada paquete, instala dependencias de forma compartida y permite que unos paquetes dependan de otros por nombre.

**Por qué cada patrón:**
- `"apps/*"` — recoge cada aplicación (`web`, `mobile`, `api`).
- `"packages/*"` — recoge las librerías compartidas (`core`, `api-client`, `ui-core`).
- `"e2e"` — carpeta única (sin `*`) para los tests end-to-end de Playwright; se incluye como un paquete más para poder darle sus propias dependencias.

Los globs `*` significan "cada subcarpeta con su `package.json` es un paquete del workspace".

---

### `.npmrc`

**Qué es.** Archivo de configuración de pnpm/npm (pares clave=valor). Aquí está muy comentado, con fines didácticos.

**Para qué sirve.** Ajusta el comportamiento del gestor de paquetes para este repo.

**Por qué cada opción:**
- `save-exact=true` — al hacer `pnpm add X`, guarda la versión **exacta** (`1.2.3`) en vez de con rango (`^1.2.3`). El propio comentario aclara que la reproducibilidad real la da el `pnpm-lock.yaml` commiteado; esto es un extra de higiene.
- `engine-strict=true` — hace que el campo `engines` del `package.json` se **cumpla** (avisa si tu Node no encaja), no que sea decorativo.
- Bloque `node-linker=hoisted` **comentado (inactivo)**. Es un stub preparado por si `apps/mobile` da problemas: Metro (el bundler de React Native/Expo) históricamente no se lleva bien con los symlinks que pnpm usa. Descomentarlo aplanaría `node_modules` al estilo npm manteniendo el store rápido de pnpm. Hoy **no está activo**.

---

### `.nvmrc`

**Qué es.** Archivo de una sola línea leído por `nvm` (Node Version Manager) y por muchas herramientas de CI.

**Para qué sirve.** Indicar la versión de Node del proyecto para que `nvm use` la seleccione.

**Por qué.** Contiene solo `22`, la major de Node exigida. Es más laxo que Volta (que fija `22.11.0` exacto): aquí basta cualquier Node 22.x. Coherente con `engines.node >= 22`.

### `tsconfig.base.json`

**Qué es.** La configuración **base** de TypeScript que el resto de `tsconfig.json` de cada paquete heredarán (con `extends`). Vive en la raíz para no repetir estas reglas.

**Para qué sirve.** Definir cómo TypeScript entiende y comprueba el código en todo el monorepo. Nota clave para alguien nuevo en TS: aquí TS se usa como **verificador de tipos**, no como compilador (ver `noEmit`), porque los paquetes se consumen sin compilar.

**Por qué cada opción (agrupadas):**
- *Salida de JS moderno:* `target: ES2022` y `lib: ["ES2022"]` — genera/asume JS moderno (Node 22 lo soporta de sobra). `module: ESNext` + `moduleResolution: Bundler` — pensado para que un bundler (Vite/Metro) resuelva los imports, no Node directamente.
- *Ergonomía de imports/módulos:* `esModuleInterop` (permite `import x from` sobre módulos CommonJS), `resolveJsonModule` (importar `.json`), `moduleDetection: force` (trata todo archivo como módulo), `isolatedModules` y `verbatimModuleSyntax` (obligan a un estilo de import/export que los bundlers pueden procesar archivo a archivo sin ambigüedad; en la práctica te fuerzan a usar `import type` para los tipos).
- `skipLibCheck: true` — no revisa los tipos **dentro** de las dependencias (`node_modules`). Acelera mucho el `typecheck` y evita fallar por errores ajenos.
- *Rigor (el bloque "strict"):* `strict: true` activa todas las comprobaciones estrictas de golpe. Los extra van más allá: `noUncheckedIndexedAccess` (acceder a `arr[i]` da `T | undefined`, obliga a comprobar), `noImplicitOverride` (exige la palabra `override` al sobrescribir métodos), `noFallthroughCasesInSwitch` (prohíbe `case` sin `break`), `forceConsistentCasingInFileNames` (evita bugs entre Windows —mayúsc/minúsc— y Linux). Para un TFG, prioriza detectar errores en compilación.
- *Sin emisión:* `noEmit: true` — TS **no** genera archivos `.js`; solo comprueba tipos (los bundlers hacen la transpilación). `declaration: false` (no genera `.d.ts`) y `sourceMap: true` (mapas para depurar).
- *Alias de imports:* `baseUrl: "."` + `paths` mapean nombres cómodos a rutas de código fuente: `@bukit/core` → `packages/core/src`, `@bukit/api-client` → `packages/api-client/src`, `@bukit/ui-core` → `packages/ui-core/src`. Apuntan directamente a `src` (código sin compilar), lo que confirma la estrategia "consumir paquetes sin build". Estos tres alias coinciden con los `packages/` descritos en el README.

### `eslint.config.mjs`

**Qué es.** La configuración de ESLint 9 en formato **flat config** (el nuevo sistema basado en un array exportado, no el antiguo `.eslintrc`). Extensión `.mjs` = módulo ESM.

**Para qué sirve.** Una única configuración de linter en la raíz para **todo** el monorepo (analiza el código en busca de errores y malas prácticas).

**Por qué cada parte:**
- `// @ts-check` — hace que TS revise este propio archivo de config (seguridad extra).
- Imports: `js` (reglas base de ESLint), `tseslint` (reglas para TypeScript), `prettier` (config que apaga reglas de estilo), `globals` (globales conocidas). Los comentarios dejan explícita la filosofía: **Prettier no se ejecuta como regla de ESLint**; formatea aparte con `pnpm format`. Separar linting de formateo es la buena práctica actual.
- Primer bloque `ignores` — lista lo que ESLint no mira: builds (`dist`, `build`), `node_modules`, `.expo`, `coverage`, reportes de Playwright (`playwright-report`, `test-results`) y **todos los archivos de config** (`*.config.{js,cjs,mjs,ts}`), para no lintear herramientas.
- `js.configs.recommended` y `...tseslint.configs.recommended` — aplican los conjuntos de reglas recomendados de JS y de TypeScript.
- Bloque para `**/*.{ts,tsx}` — solo a archivos TS/TSX: `ecmaVersion: latest`, `sourceType: module`, y `globals.node` (asume entorno Node). La regla destacable: desactiva `no-unused-vars` nativa y activa la versión de TS `@typescript-eslint/no-unused-vars` como **error**, pero con `argsIgnorePattern`/`varsIgnorePattern: "^_"` — es decir, una variable/argumento que empiece por `_` (p. ej. `_unused`) se permite sin quejas. Es el convenio habitual para "sé que no lo uso a propósito".
- `prettier` va **el último** en el array — clave: en flat config, lo último gana; ponerlo al final garantiza que apaga las reglas de estilo que chocarían con Prettier.

### `.prettierrc.json`

**Qué es.** Configuración de Prettier, el formateador automático de código.

**Para qué sirve.** Fijar un estilo único (comillas, comas, ancho de línea…) para que todo el equipo/proyecto formatee igual y no haya diffs por estilo.

**Por qué cada campo:**
- `"semi": true` — pone punto y coma al final.
- `"singleQuote": false` — usa comillas **dobles** (`"..."`).
- `"trailingComma": "all"` — coma final incluso en el último elemento (mejores diffs en git y menos errores al reordenar).
- `"printWidth": 100` — parte líneas a los 100 caracteres (más holgado que el 80 clásico).
- `"tabWidth": 2` — indentación de 2 espacios (coincide con `.editorconfig`).
- `"endOfLine": "lf"` — finales de línea Unix (`\n`), importante en un repo desarrollado en Windows para evitar ruido de `\r\n`.
- El `$schema` inicial solo aporta autocompletado/validación del propio JSON en el editor.

---

### `.prettierignore`

**Qué es.** Lista de rutas que Prettier **no** debe formatear (mismo estilo que `.gitignore`).

**Para qué sirve.** Evitar formatear archivos generados o ajenos.

**Por qué cada entrada:** `node_modules`, `dist`, `build` (dependencias y builds), `.expo`, `coverage`, `playwright-report`, `test-results` (generados por herramientas). Y dos concretas del proyecto: `pnpm-lock.yaml` (lo gestiona pnpm; no se toca a mano) y `apps/api/prisma/migrations/**` (SQL de migraciones generado por Prisma; reformatearlo podría alterar archivos que deben permanecer intactos).

### `.editorconfig`

**Qué es.** Archivo estándar `.editorconfig`, entendido por la mayoría de editores/IDEs (a veces con plugin). Complementa a Prettier a un nivel más básico y universal.

**Para qué sirve.** Que el editor aplique automáticamente convenciones básicas al escribir, incluso en archivos que Prettier no toca.

**Por qué cada regla:**
- `root = true` — indica que este es el `.editorconfig` de más arriba; el editor deja de buscar en carpetas superiores.
- Bloque `[*]` (todos los archivos): `charset = utf-8`, `end_of_line = lf` (coherente con Prettier), `insert_final_newline = true` (línea en blanco final), `trim_trailing_whitespace = true` (quita espacios sobrantes al final de línea), `indent_style = space` + `indent_size = 2` (2 espacios, coincide con Prettier).
- Bloque `[*.md]`: `trim_trailing_whitespace = false` — excepción para Markdown, donde **dos espacios al final de línea son significativos** (fuerzan un salto de línea). Evita romper el formato de los `.md`.

### `.gitignore`

**Qué es.** Lista de archivos/carpetas que git no debe versionar.

**Para qué sirve.** Mantener fuera del repo lo generado, lo pesado y lo secreto.

**Por qué, por secciones (según los comentarios del archivo):**
- *Dependencias:* `node_modules/` y `.pnpm-store/` (el store local de pnpm).
- *Builds/salidas:* `dist/`, `build/`, `*.tsbuildinfo` (caché incremental de TS).
- *Entorno:* ignora `.env` y `.env.*` **pero** con excepción `!.env.example` — el patrón habitual: los secretos reales no se suben, pero sí una plantilla de ejemplo (que el README manda copiar con `cp apps/api/.env.example apps/api/.env`).
- *Prisma:* `apps/api/prisma/generated/` por si el cliente Prisma se emite fuera de `node_modules`.
- *Testing:* `coverage/`, `playwright-report/`, `test-results/`, `.playwright/`.
- *Expo/React Native:* `.expo/`, `*.orig.*`, `web-build/`.
- *Logs:* `*.log`, `npm-debug.log*`, `pnpm-debug.log*`.
- *Editores/SO:* `.DS_Store` (macOS), `Thumbs.db` (Windows), `.idea/` (JetBrains) y archivos de Visual Studio (`*.suo`, `*.sln`, etc.).
- *Turborepo:* `.turbo/` — preparado "si se añade más adelante"; hoy Turborepo no está en uso, es previsión.

## Base de datos local (Docker: Postgres + PostGIS + pgvector)

Estos tres archivos trabajan juntos para levantar, con un solo comando (`docker compose up`), una base de datos PostgreSQL en tu ordenador que ya trae instaladas las dos extensiones especiales que BUKIT necesita: **PostGIS** (geolocalización, "gente cerca de mí") y **pgvector** (afinidad por similitud de vectores). La idea es que cualquier persona que clone el repo tenga exactamente la misma base de datos sin instalar nada a mano.

### `docker-compose.yml`

**1. Qué es.** Es el archivo de configuración de **Docker Compose**, la herramienta que orquesta uno o varios contenedores Docker describiéndolos en un YAML en vez de con comandos sueltos. Aquí define un único servicio llamado `db`.

**2. Para qué sirve en el proyecto.** Levanta el Postgres local que se usa para **desarrollo, tests y CI** (así lo dicen los comentarios de las líneas 1-3). Los comentarios también aclaran algo importante: **producción NO usa este contenedor**; en producción la base irá en Neon (Postgres gestionado en la UE, por GDPR). Por eso las credenciales de aquí son solo de desarrollo y no importa que sean triviales.

**3. Por qué de cada decisión concreta (lo que aparece de verdad):**

- **`build: ./docker/postgres`** (línea 6): en lugar de descargar una imagen ya hecha, Compose construye la imagen usando el `Dockerfile` de esa carpeta. Es necesario porque ninguna imagen oficial trae PostGIS *y* pgvector a la vez; hay que fabricarla (ver el Dockerfile abajo).
- **`image: bukit-postgres:16`** (línea 7): nombre y etiqueta que se le pone a la imagen ya construida, para reutilizarla y no recompilarla cada vez. El `16` referencia la versión de Postgres.
- **`container_name: bukit-db`** (línea 8): nombre fijo y legible del contenedor, en vez de uno aleatorio.
- **`restart: unless-stopped`** (línea 9): si el contenedor se cae o reinicias el ordenador, Docker vuelve a levantarlo automáticamente, salvo que tú lo hayas parado a mano a propósito. Cómodo para no perder la BD entre sesiones.
- **`environment`** (líneas 10-13): variables que la imagen de Postgres lee al arrancar para crear automáticamente el usuario, su contraseña y una base de datos inicial. Aquí los tres valores son `bukit` (usuario `bukit`, contraseña `bukit`, base `bukit`). Son deliberadamente simples porque, insistimos, es solo local.
- **`ports: "5432:5432"`** (líneas 14-15): mapea el puerto 5432 del contenedor al 5432 de tu máquina (formato `host:contenedor`). 5432 es el puerto estándar de Postgres, así que tu backend puede conectarse a `localhost:5432` como si Postgres estuviera instalado nativamente.
- **`volumes`** (líneas 16-19): monta dos cosas.
  - `bukit-db-data:/var/lib/postgresql/data`: un **volumen con nombre** (declarado al final del archivo) que guarda los datos reales de la base en `/var/lib/postgresql/data`. Gracias a esto los datos **persisten** aunque borres o recrees el contenedor; sin esto, cada reinicio empezaría vacío.
  - `./docker/postgres/init:/docker-entrypoint-initdb.d`: monta la carpeta local `init` dentro de una carpeta especial de la imagen de Postgres. Todo lo que haya ahí (los `.sql`/`.sh`) se ejecuta **una única vez, al crear la base por primera vez**. Así se activan las extensiones automáticamente (ver el `.sql` de abajo).
- **`healthcheck`** (líneas 20-24): le dice a Docker cómo comprobar que la BD está realmente lista para aceptar conexiones, no solo "arrancada".
  - `test: ["CMD-SHELL", "pg_isready -U bukit -d bukit"]`: usa la utilidad `pg_isready` de Postgres, que responde OK solo cuando el servidor acepta consultas. El comando se escribe en la forma de array de Compose con `CMD-SHELL`, que indica a Docker que lo ejecute a través de una shell.
  - `interval: 5s` (cada cuánto reintenta), `timeout: 5s` (cuánto espera cada intento antes de darlo por fallido) y `retries: 10` (cuántos fallos seguidos hasta marcarlo "unhealthy"). Es útil para que en CI u otros servicios se espere a que la BD esté sana antes de correr migraciones o tests.
- **`volumes: bukit-db-data`** (líneas 26-27): declaración del volumen con nombre que se usó arriba. Docker lo gestiona internamente y sobrevive al ciclo de vida del contenedor.

### `docker/postgres/Dockerfile`

**1. Qué es.** Un **Dockerfile**: la receta que Docker sigue para construir una imagen personalizada, paso a paso.

**2. Para qué sirve en el proyecto.** Fabrica la imagen `bukit-postgres:16` que combina **PostGIS + pgvector** en un mismo Postgres. Los comentarios (líneas 1-2) lo explican: PostGIS ya viene en la imagen base, y aquí se le **añade** pgvector para tener ambas extensiones juntas (mapa de cercanía + afinidad vectorial), es decir, los dos pilares técnicos que pide BUKIT sin montar dos bases de datos distintas.

**3. Por qué de cada decisión concreta:**

- **`FROM postgis/postgis:16-3.4`** (línea 3): parte de la imagen oficial de PostGIS. Ya trae Postgres 16 y PostGIS 3.4 preinstalados, así que no hay que compilar PostGIS a mano. La etiqueta `16-3.4` fija esas versiones para que la build sea reproducible (todos obtienen lo mismo).
- **`RUN apt-get update && apt-get install -y --no-install-recommends postgresql-16-pgvector && rm -rf /var/lib/apt/lists/*`** (líneas 5-7): instala pgvector, que no viene de fábrica. Detalles del porqué:
  - Como la imagen base es Debian, se usa `apt-get`.
  - `postgresql-16-pgvector`: el paquete de pgvector compilado **específicamente para Postgres 16**, para que encaje con la versión base.
  - `-y`: responde "sí" automáticamente, imprescindible porque en una build no hay nadie para confirmar interactivamente.
  - `--no-install-recommends`: instala solo lo justo y evita paquetes "recomendados" opcionales, manteniendo la imagen más pequeña.
  - `rm -rf /var/lib/apt/lists/*`: borra la caché de índices de apt al final. Se encadena en el mismo `RUN` (una sola capa de imagen) para que esos archivos temporales no queden guardados; así la imagen final pesa menos.

### `docker/postgres/init/01-extensions.sql`

**1. Qué es.** Un **script SQL de inicialización**. Está en la carpeta `init` que el `docker-compose.yml` monta en `/docker-entrypoint-initdb.d`, la ubicación que la imagen de Postgres ejecuta automáticamente al arrancar por primera vez. El prefijo `01-` fija el orden de ejecución (si hubiera más scripts, se corren por orden alfabético).

**2. Para qué sirve en el proyecto.** Activa las dos extensiones dentro de la base de datos. Instalar el software (lo del Dockerfile) no basta: en Postgres cada extensión hay que **habilitarla** con `CREATE EXTENSION` dentro de la BD concreta. Este script hace justo eso, de forma automática, la primera vez que se crea la base.

**3. Por qué de cada decisión concreta (según sus comentarios, líneas 1-3):**

- Se ejecuta **una sola vez**, al crear la BD por primera vez (así funciona `docker-entrypoint-initdb.d`: solo corre si el volumen de datos está vacío). Si la base ya existía, este script no se vuelve a ejecutar.
- El comentario aclara que **Prisma también podría gestionar las extensiones** (vía `postgresqlExtensions`), pero se hace aquí además para **garantizar que estén disponibles desde el minuto cero**, antes incluso de correr migraciones.
- **`CREATE EXTENSION IF NOT EXISTS postgis;`** (línea 4): habilita PostGIS (geolocalización: consultas tipo "usuarios dentro de un radio").
- **`CREATE EXTENSION IF NOT EXISTS vector;`** (línea 5): habilita pgvector (la extensión se llama `vector`) para la afinidad por similitud de embeddings. Ojo con el detalle: el paquete se llama `pgvector` pero la extensión SQL se llama `vector`.
- **`IF NOT EXISTS`** en ambas: hace el script **idempotente** (como dice el comentario), es decir, ejecutarlo cuando la extensión ya existe no da error. Es una red de seguridad por si el script llegara a correr más de una vez.

**Nota:** ninguno de los tres archivos es un stub ni está vacío; los tres tienen contenido funcional real.

## packages/ — código compartido (core, api-client, ui-core)

Esta carpeta agrupa los **paquetes internos** del monorepo: código que no es una app ejecutable en sí, sino librerías que las apps (`web`, `mobile`, `api`) importan. La idea de un monorepo es escribir una sola vez lo que es común (tipos, validaciones, lógica) y reutilizarlo en todos los sitios, evitando copiar-pegar y que las cosas se desincronicen.

Tres detalles se repiten en los tres paquetes y conviene entenderlos una vez:

- **`"name": "@bukit/..."`**: el nombre lleva un *scope* (`@bukit/`). Es una convención para agrupar paquetes de un mismo proyecto. Como el nombre coincide con lo que se pone en los `import` (`import ... from "@bukit/core"`), el gestor de paquetes del workspace sabe resolverlo a la carpeta local en vez de buscarlo en internet.
- **`"private": true`**: marca el paquete como no publicable en el registro público de npm. Es correcto porque son piezas internas del TFG, no librerías para terceros.
- **`"type": "module"`**: le dice a Node que estos archivos usan `import`/`export` de ES Modules (la sintaxis moderna de JS), no el antiguo `require`/`module.exports` de CommonJS.

---

### `packages/core/package.json`

1. **Qué es.** El manifiesto (ficha de identidad) del paquete `@bukit/core`, leído por npm/el gestor del workspace.
2. **Para qué sirve.** Declara el paquete que contiene los **tipos de TypeScript y los esquemas de validación Zod compartidos por todo el monorepo** (así lo dice su `description`: "universal"). Es la fuente única de verdad sobre qué forma tienen los datos.
3. **Porqué de las decisiones concretas:**
   - `"exports"`, `"main"` y `"types"` apuntan todos a `./src/index.ts`, es decir, **al TypeScript sin compilar**. Normalmente un paquete publicado apuntaría a JS ya compilado; aquí se consume el `.ts` en crudo porque cada app lo compila junto con su propio código (ver `index.ts`). Esto simplifica el desarrollo: no hay que ejecutar un paso de build de este paquete antes de usarlo.
   - `"scripts"` solo tiene `typecheck: "tsc --noEmit"`: ejecuta el compilador de TypeScript únicamente para **comprobar tipos** (`--noEmit` = no generes archivos de salida). Coherente con lo anterior: no compila, solo verifica.
   - `"dependencies"` con `zod: "^3.24.1"`: única dependencia. Zod es la librería con la que se definen los esquemas de validación. El `^` permite actualizaciones menores/parches compatibles (3.x.x) pero no un salto a la 4.

---

### `packages/core/tsconfig.json`

1. **Qué es.** Archivo de configuración de TypeScript para este paquete.
2. **Para qué sirve.** Le indica al compilador cómo tratar el código de `core`.
3. **Porqué de las decisiones concretas:**
   - `"extends": "../../tsconfig.base.json"`: **hereda** toda la configuración común del `tsconfig.base.json` de la raíz del monorepo. Así las reglas del compilador (strict, target, etc.) se definen una sola vez en la raíz y todos los paquetes las comparten; aquí solo se ponen las diferencias.
   - `"include": ["src"]`: le dice a TypeScript que solo debe mirar la carpeta `src`. La única "diferencia" respecto a la base es indicar dónde está su código.

---

### `packages/core/src/index.ts`

1. **Qué es.** El punto de entrada (barrel file) del paquete, en TypeScript.
2. **Para qué sirve.** Reexporta el contenido de los demás módulos para que quien importe `@bukit/core` obtenga todo desde un único sitio.
3. **Porqué de las decisiones concretas:**
   - `export * from "./user.js"` y `export * from "./list.js"`: reexporta absolutamente todo lo público de `user` y `list`. Un consumidor puede escribir `import { registerUserSchema, createListSchema } from "@bukit/core"` sin saber en qué archivo interno vive cada cosa.
   - Se importa con extensión **`.js`** aunque el archivo real sea `user.ts`. No es un error: es la regla de los ES Modules "modernos" en TypeScript, donde en el código se referencia el nombre del archivo *como quedaría al ejecutarse* (`.js`), y el compilador entiende que corresponde al `.ts`.
   - El comentario superior explica la decisión clave: **se consume en crudo (TS sin compilar)**; web (Vite), móvil (Metro) y api (tsx) lo compilan junto con su propio código. Ese es el motivo de que todo apunte a `.ts` en el `package.json`.

---

### `packages/core/src/user.ts`

1. **Qué es.** Módulo TypeScript con esquemas Zod y tipos relacionados con el usuario.
2. **Para qué sirve.** Define y valida los datos de usuario, y esa **misma validación se usa en el frontend y en el backend** (lo dice el comentario "front ↔ back"). Validar una vez y compartir evita reglas duplicadas que se contradigan.
3. **Porqué de las decisiones concretas:**
   - `userTierSchema = z.enum(["NORMAL", "TOP"])`: los dos niveles de usuario del producto. NORMAL = registrado corriente; TOP = creador/influencer con vídeo ilimitado y más peso en el feed. El comentario lo ata a la §3.1 de la propuesta.
   - `export type UserTier = z.infer<typeof userTierSchema>`: patrón central de Zod. `z.infer` **deriva el tipo de TypeScript a partir del esquema**, así el tipo (`"NORMAL" | "TOP"`) y la validación en tiempo de ejecución nunca se desincronizan: hay una sola definición.
   - `registerUserSchema`: `email: z.string().email()` (cadena con formato de email) y `password: z.string().min(8).max(128)` (entre 8 y 128 caracteres). El mínimo de 8 es una regla de seguridad razonable; el máximo evita contraseñas absurdamente largas.
   - `loginSchema`: mismo email, pero `password: z.string().min(1)` (solo exige que no esté vacía). Tiene sentido: al **iniciar sesión** no se re-valida la política de longitud —eso ya se hizo al registrarse—, solo que se haya escrito algo.
   - Cada esquema va acompañado de su tipo (`RegisterUserInput`, `LoginInput`) vía `z.infer`, listos para tipar funciones y formularios.

---

### `packages/core/src/list.ts`

1. **Qué es.** Módulo TypeScript con esquemas Zod y tipos de las "listas" (las metas del usuario).
2. **Para qué sirve.** Modela y valida las listas de metas, el concepto central del producto (una lista = conjunto de metas con plazo).
3. **Porqué de las decisiones concretas:**
   - `FREE_PLAN_MAX_LISTS = 3`: constante exportada con el tope de listas del plan gratuito. El comentario advierte que **es una regla de negocio a aplicar en el back** (Zod define la forma de los datos, no cuántas listas tiene ya el usuario; ese conteo se comprueba en el servidor).
   - `goalSchema`: cada meta tiene `title: z.string().min(1).max(200)` (no vacío, máx. 200 caracteres) y `completed: z.boolean().default(false)`. El `.default(false)` significa que si no se envía el campo, Zod lo rellena con `false`: una meta nace sin completar.
   - `createListSchema` (crear/editar lista):
     - `title: z.string().min(1).max(120)`: obligatorio, límite 120.
     - `deadline: z.coerce.date().optional()`: el plazo es **opcional**. `z.coerce.date()` convierte automáticamente lo que llegue (p. ej. un string de fecha JSON) en un objeto `Date` de JS —útil porque el JSON no tiene tipo fecha nativo.
     - `goals: z.array(goalSchema).max(100).default([])`: array de metas, **máximo 100** por lista, y si no se envía se usa `[]` (lista sin metas). El tope de 100 protege frente a envíos abusivos.
   - Los tipos `GoalInput` y `CreateListInput` se derivan de nuevo con `z.infer`.

---

### `packages/api-client/package.json`

1. **Qué es.** Manifiesto del paquete `@bukit/api-client`.
2. **Para qué sirve.** Declara el **cliente HTTP tipado que reutilizarán web y móvil** para hablar con la API. Su `description` avisa: **"stub por ahora"** (todavía sin implementar).
3. **Porqué de las decisiones concretas:**
   - Misma estructura que `core` (`exports`/`main`/`types` → `./src/index.ts`, `typecheck` con `tsc --noEmit`, `private`, `type: module`), por coherencia entre paquetes.
   - `"dependencies"`: `"@bukit/core": "workspace:*"`. El protocolo **`workspace:*`** indica que esta dependencia es **otro paquete del propio monorepo** (no de internet) y que se use la versión local que exista, sea cual sea. Refleja que el cliente reutilizará los tipos/esquemas de `core` para validar respuestas.

---

### `packages/api-client/tsconfig.json`

1. **Qué es.** Configuración de TypeScript del paquete api-client.
2. **Para qué sirve.** Igual que en core: decirle al compilador cómo tratar este paquete.
3. **Porqué de las decisiones concretas:** idéntico a los demás: `"extends": "../../tsconfig.base.json"` (hereda las reglas comunes de la raíz) e `"include": ["src"]` (solo compila/verifica su carpeta `src`). Toda la configuración de fondo vive centralizada en la raíz.

---

### `packages/api-client/src/index.ts`

1. **Qué es.** Punto de entrada del paquete, pero de momento un **stub (placeholder) intencionadamente vacío**.
2. **Para qué sirve.** Reservar el sitio del futuro cliente HTTP. Los comentarios explican el plan: se implementará al montar la primera app cliente, la librería HTTP está aún por decidir, y reutilizará tipos y esquemas de `@bukit/core` para validar las respuestas.
3. **Porqué de las decisiones concretas:**
   - `export {};` es la única línea de código real. Es un truco necesario: un archivo `.ts` **sin ningún import/export** sería tratado como script global; poner `export {}` (un export vacío) lo convierte en un **módulo válido** sin exportar nada todavía. Así el paquete existe, compila y puede importarse aunque aún no tenga contenido.

---

### `packages/ui-core/package.json`

1. **Qué es.** Manifiesto del paquete `@bukit/ui-core`.
2. **Para qué sirve.** Declara el paquete de **lógica y estado compartidos entre web y móvil, sin DOM ni UI** (según su `description`). También marcado **"stub por ahora"**. La distinción clave frente a `core`: `core` son datos/validación puros; `ui-core` será lógica de presentación agnóstica (selectores, estado) que no dibuja nada.
3. **Porqué de las decisiones concretas:**
   - Misma plantilla que los otros paquetes (`exports`/`main`/`types` al `.ts`, `typecheck`, `private`, `type: module`).
   - `"dependencies"`: `"@bukit/core": "workspace:*"` — igual que api-client, depende del paquete local `core` (usará sus tipos), resuelto dentro del workspace.

---

### `packages/ui-core/tsconfig.json`

1. **Qué es.** Configuración de TypeScript de ui-core.
2. **Para qué sirve.** Configurar el compilador para este paquete.
3. **Porqué de las decisiones concretas:** idéntico a los demás: `"extends": "../../tsconfig.base.json"` (reglas heredadas de la raíz) e `"include": ["src"]` (solo su código). Uniformidad total entre paquetes.

---

### `packages/ui-core/src/index.ts`

1. **Qué es.** Punto de entrada del paquete, **stub (placeholder) intencionadamente vacío** por ahora.
2. **Para qué sirve.** Reservar el hueco de la lógica/estado compartidos. Los comentarios detallan qué contendrá: selectores, hooks agnósticos, formateadores, estado de Redux/TanStack Query; y qué **NO** contendrá: nada de DOM ni componentes nativos (eso vive en cada app). Se rellenará al montar `apps/web` y `apps/mobile`.
3. **Porqué de las decisiones concretas:**
   - Igual que en api-client, la única línea es `export {};`, el export vacío que convierte el archivo en un módulo válido pese a no exportar aún nada. Es un marcador de posición, no código funcional.

## apps/api — backend Node + capa Prisma

Esta carpeta es el backend de BUKIT: un servicio Node escrito en TypeScript que hablará con una base de datos PostgreSQL a través de Prisma (un ORM, es decir, una herramienta que traduce entre tablas SQL y objetos JavaScript). Ahora mismo es un **esqueleto arrancable pero casi vacío**: la conexión a la base de datos ya funciona, pero todavía no hay ni framework HTTP (Express/NestJS) ni modelos de datos. Cada archivo se explica abajo.

---

### `apps/api/package.json`

**1. Qué es.** El manifiesto del paquete Node de la API. Es el archivo estándar de npm que declara nombre, dependencias y los comandos (`scripts`) que se pueden ejecutar.

**2. Para qué sirve.** Define cómo se instala, arranca, compila y gestiona la base de datos de este subproyecto dentro del monorepo.

**3. El porqué de cada decisión concreta que aparece:**
- `"name": "@bukit/api"` — el prefijo `@bukit/` es un *scope* (espacio de nombres). En un monorepo, cada paquete interno se nombra así (`@bukit/api`, `@bukit/core`, …) para poder referenciarse entre sí sin colisiones.
- `"private": true` — marca el paquete como no publicable en npm. Es un servicio interno, nunca se subirá al registro público; esto evita publicarlo por accidente.
- `"type": "module"` — hace que Node interprete los `.js` como **ES Modules** (`import`/`export`), no como el viejo CommonJS (`require`). Por eso en `index.ts` verás `import ... from "./prisma.js"` con extensión `.js` explícita, que es lo que exige el modo ESM.
- `"version": "0.0.0"` — versión placeholder; al ser privado y no publicarse, el número no importa.
- La `description` deja claro que el *framework HTTP está pendiente de decidir* (Express o NestJS): es una decisión que aún no se ha tomado.

**Scripts (los comandos que puedes lanzar):**
- `dev`: `tsx watch src/index.ts` — arranca el servidor en desarrollo. `tsx` ejecuta TypeScript directamente sin compilar antes; `watch` reinicia al guardar cambios.
- `build`: `tsc -p tsconfig.build.json` — compila TypeScript a JavaScript usando la config de build (ver más abajo).
- `start`: `node dist/index.js` — ejecuta el código **ya compilado** (lo que se usa en producción).
- `typecheck`: `tsc --noEmit` — solo comprueba tipos, sin generar archivos. Útil en CI para detectar errores de tipos.
- `prisma:generate`: `prisma generate` — genera el cliente Prisma tipado a partir del `schema.prisma`.
- `db:migrate`: `prisma migrate dev` — crea/aplica migraciones en desarrollo.
- `db:deploy`: `prisma migrate deploy` — aplica migraciones ya existentes en producción (sin crear nuevas).
- `db:studio`: `prisma studio` — abre Prisma Studio, una GUI web para ver/editar la base de datos.
- `db:seed`: `tsx prisma/seed.ts` — ejecuta el script de seed para poblar datos de ejemplo.
- El bloque `"prisma": { "seed": "tsx prisma/seed.ts" }` — le dice al CLI de Prisma qué comando usar cuando *él mismo* quiera sembrar datos (p. ej. tras `prisma migrate reset`). Está duplicado a propósito respecto a `db:seed` porque Prisma lee su config de aquí, no de `scripts`.

**Dependencias:**
- `@bukit/core`: `"workspace:*"` — esto es clave para entender monorepos. `workspace:*` significa "usa el paquete `@bukit/core` que está **aquí mismo, en este monorepo**", no una versión descargada de npm. El gestor de paquetes lo enlaza localmente.
- `@prisma/client` (`^6.1.0`) — el cliente en tiempo de ejecución que usas para hacer consultas.
- En `devDependencies`: `prisma` (el CLI, solo necesario en desarrollo/build; `^6.1.0`) y `tsx` (el ejecutor de TypeScript; `^4.19.2`). El `^` permite actualizaciones menores/parches compatibles.

---

### `apps/api/tsconfig.json`

**1. Qué es.** El archivo de configuración de TypeScript para este paquete (le dice al compilador `tsc` cómo comportarse).

**2. Para qué sirve.** Es la config base que usan el editor (VS Code) y el `typecheck`. Sirve para *chequear tipos* de todo el código de la API.

**3. El porqué de las decisiones:**
- `"extends": "../../tsconfig.base.json"` — **hereda** la configuración común del monorepo (que vive dos niveles arriba, en la raíz). En lugar de repetir opciones en cada paquete, se centralizan en la raíz y aquí solo se añaden las diferencias. Esto es un patrón típico de monorepo.
- `"types": ["node"]` — le indica a TypeScript que cargue los tipos globales de **Node.js** (para conocer `process`, `console`, etc.). Sin esto, TS no reconocería APIs propias del entorno Node.
- `"include": ["src", "prisma"]` — qué carpetas revisa el chequeo de tipos: el código fuente (`src`) y los scripts de Prisma (`prisma`, donde está `seed.ts`).

---

### `apps/api/tsconfig.build.json`

**1. Qué es.** Una **segunda** configuración de TypeScript, específica para la compilación de producción. El archivo `build` (`npm run build`) usa esta, no la anterior.

**2. Para qué sirve.** Separa "solo chequear tipos" (tsconfig.json) de "generar JavaScript real" (este). Es habitual tener dos: una para el editor/typecheck y otra para producir el `dist/`.

**3. El porqué de las decisiones:**
- `"extends": "./tsconfig.json"` — parte de la config del propio paquete y solo cambia lo necesario para compilar.
- `"noEmit": false` — la config base del monorepo (`tsconfig.base.json`) tiene `noEmit: true` (no generar archivos, solo chequear). Aquí se **reactiva** la emisión para que sí produzca JavaScript.
- `"outDir": "dist"` — el JavaScript compilado se escribe en la carpeta `dist/`. Encaja con el script `start` que ejecuta `node dist/index.js`.
- `"sourceMap": true` — genera *source maps*: archivos que conectan el JS compilado con el TS original, para que los errores en producción apunten a la línea correcta del código fuente. (La config base ya activa `sourceMap`; aquí se reafirma junto al resto de ajustes de build.)
- `"include": ["src"]` — solo compila `src` (excluye `prisma`, porque `seed.ts` no forma parte del artefacto de servidor; se ejecuta aparte con `tsx`).

---

### `apps/api/.env.example`

**1. Qué es.** Una **plantilla** de variables de entorno. No es el archivo real de secretos, sino un ejemplo versionado en Git para que cualquiera sepa qué variables necesita.

**2. Para qué sirve.** Documenta la configuración sensible sin exponerla. El propio comentario indica: copia este archivo a `.env` (que está gitignorado) y ajústalo.

**3. El porqué de las decisiones:**
- `DATABASE_URL="postgresql://bukit:bukit@localhost:5432/bukit?schema=public"` — la cadena de conexión a Postgres. Usuario `bukit`, contraseña `bukit`, host `localhost`, puerto `5432` (el estándar de Postgres), base `bukit`, esquema `public`. El comentario aclara que estas credenciales coinciden con las del `docker-compose` de desarrollo, para que arranque a la primera en local.
- El comentario final avisa que en **producción** esta URL apuntará a **Neon** (Postgres gestionado, región EU) y que **nunca se commitea** el `.env` real. Por eso solo se versiona el `.example`.

---

### `apps/api/prisma/schema.prisma`

**1. Qué es.** El esquema de Prisma: el archivo donde se define, en el lenguaje propio de Prisma, tanto la conexión a la base de datos como los modelos (tablas). De aquí Prisma genera el cliente tipado y las migraciones SQL.

**2. Para qué sirve.** Es la "fuente de la verdad" del modelo de datos. Ahora mismo define la infraestructura de conexión, pero **el modelo de datos está intencionadamente vacío** (lo dice el propio comentario).

**3. El porqué de las decisiones:**
- Bloque `generator client` con `provider = "prisma-client-js"` — indica que se generará el cliente JavaScript/TypeScript de Prisma.
- `previewFeatures = ["postgresqlExtensions"]` — activa una función *preview* de Prisma necesaria para poder declarar extensiones de Postgres directamente en el esquema.
- Bloque `datasource db`: `provider = "postgresql"` (la base es Postgres) y `url = env("DATABASE_URL")` — la conexión no se escribe a mano, se lee de la variable de entorno (el `.env` de antes). Buena práctica: nunca hardcodear credenciales.
- `extensions = [postgis, vector]` — habilita dos extensiones de Postgres decididas de antemano: **PostGIS** (geolocalización, para el mapa de descubrimiento: "gente en un radio") y **pgvector** (`vector`, para afinidad por similitud de vectores/embeddings). El comentario justifica que son *infraestructura*, no modelo de datos, por eso ya están aunque no haya tablas.
- La sección "MODELOS DE DATOS" está **vacía a propósito**. El comentario explica la razón: el modelo (entidades, relaciones, cascadas de borrado, índices) se diseñará de forma incremental y meditada para maximizar la integridad referencial. Aquí irán los bloques `model ...` cuando se definan uno a uno. **No es un olvido: es un stub deliberado.**

---

### `apps/api/prisma/seed.ts`

**1. Qué es.** Un script de "seed" (siembra) en TypeScript: código que rellena la base de datos con datos de ejemplo. Se ejecuta con `tsx prisma/seed.ts`.

**2. Para qué sirve.** Poblar datos de prueba en desarrollo. El comentario dice que está pensado para ser **idempotente** (poder ejecutarlo varias veces sin duplicar datos, mediante `upserts`).

**3. El porqué de las decisiones:**
- Importa y crea `new PrismaClient()` — el cliente para hablar con la base.
- La función `main()` **solo imprime** `"[seed] No hay modelos que poblar todavía."`. Es un **placeholder honesto**: como aún no existen modelos en el esquema, no hay nada que sembrar. Cuando existan entidades, aquí irán los `upsert`.
- El patrón `main().catch(...).finally(...)`:
  - `.catch((err: unknown) => ...)` — si algo falla, lo imprime y pone `process.exitCode = 1` (marca el proceso como fallido, importante para CI). El tipo `unknown` en el error es la forma segura en TypeScript de tipar algo que "no sabemos qué es" (obliga a comprobarlo antes de usarlo).
  - `.finally(() => { void prisma.$disconnect(); })` — cierra siempre la conexión, pase lo que pase, para no dejar conexiones colgadas. El `void` delante indica deliberadamente "ignoro la promesa que devuelve esto" (satisface reglas de linter sin esperar el resultado).

---

### `apps/api/src/index.ts`

**1. Qué es.** El punto de entrada del servidor: el archivo que se ejecuta al arrancar la API (`dev` lo lanza con tsx, `start` lo ejecuta ya compilado como `dist/index.js`).

**2. Para qué sirve.** De momento **solo verifica que la conexión a Postgres funciona**. Todavía no monta ningún servidor HTTP.

**3. El porqué de las decisiones:**
- `import { prisma } from "./prisma.js"` — importa el cliente singleton (ver siguiente archivo). Nota la extensión **`.js`** aunque el archivo real sea `.ts`: es obligatorio en ESM con Node, porque en tiempo de ejecución el import se resuelve contra el archivo compilado.
- Dos comentarios `TODO` muy explícitos: (a) falta montar el framework HTTP (Express o NestJS, decisión pendiente); (b) aún no hay modelos de datos.
- `await prisma.$queryRaw\`SELECT 1\`` — ejecuta la consulta SQL más simple posible. El comentario explica el porqué: comprobar la conexión **sin depender de ningún modelo** (como no hay tablas, no puede consultar entidades; `SELECT 1` siempre funciona si la base responde).
- Mismo patrón `main().catch(...).finally(...)` que el seed: gestiona errores marcando `exitCode = 1` y cierra la conexión al final. Es un stub sólido: arranca, prueba la base y termina limpiamente.

---

### `apps/api/src/prisma.ts`

**1. Qué es.** Un pequeño módulo que crea y exporta una única instancia (**singleton**) del cliente Prisma para reutilizarla en toda la app.

**2. Para qué sirve.** Evitar crear muchos `PrismaClient`, algo que en desarrollo con recarga en caliente (`tsx watch`) agotaría el *pool* de conexiones a la base de datos.

**3. El porqué de cada línea:**
- `const globalForPrisma = globalThis as unknown as { prisma?: PrismaClient }` — guarda una referencia al cliente en el objeto global de Node. El doble casteo `as unknown as {...}` es un truco de TypeScript para "convencer" al compilador de que `globalThis` tiene una propiedad `prisma?` opcional (TS no lo sabe por defecto). Es la forma tipada de adjuntar algo al objeto global.
- `export const prisma = globalForPrisma.prisma ?? new PrismaClient({...})` — usa el operador `??` (nullish coalescing): si ya existe un cliente en el global, lo reutiliza; si no, crea uno nuevo. Así, aunque `tsx watch` recargue el módulo, no se acumulan clientes.
- La opción `log`: `process.env.NODE_ENV === "production" ? ["error"] : ["query", "warn", "error"]` — en producción solo registra errores (menos ruido/mejor rendimiento); en desarrollo también registra cada consulta (`query`) y avisos (`warn`), útil para depurar.
- `if (process.env.NODE_ENV !== "production") { globalForPrisma.prisma = prisma; }` — solo guarda la referencia global **fuera de producción**. El motivo: el problema de las recargas solo ocurre en desarrollo; en producción el proceso arranca una vez y no hace falta ensuciar el objeto global. Este es un patrón muy conocido y recomendado para Prisma.

## e2e (Playwright) y placeholders de apps/web y apps/mobile

Este bloque documenta el paquete de tests end-to-end (E2E) con Playwright y los dos READMEs "placeholder" de las apps de cliente. En un **monorepo**, `e2e/` es un paquete más (con su propio `package.json`), independiente de `apps/web` o `apps/mobile`, dedicado a probar la aplicación web ya construida como la usaría un usuario real (abriendo un navegador de verdad).

---

### `e2e/package.json`

**1. Qué es.** El manifiesto npm/pnpm del paquete de tests E2E. Define su nombre, sus dependencias y sus scripts. Es el archivo que convierte la carpeta `e2e/` en un "paquete" dentro del monorepo.

**2. Para qué sirve.** Declara las herramientas y comandos para ejecutar los tests end-to-end con Playwright. Según su `description`, estos tests son "la última barrera del pipeline fail-fast": en CI se ejecutan al final, después de lint y tests unitarios/integración, y son los que dan el visto bueno definitivo.

**3. El porqué de cada decisión:**
- `"name": "@bukit/e2e"` — el prefijo `@bukit/` es el *scope* (espacio de nombres) común de todos los paquetes del monorepo. Permite que unos paquetes se referencien a otros por ese nombre.
- `"version": "0.0.0"` — versión ficticia; en paquetes privados internos no se publica ni versiona de verdad, así que se deja en cero.
- `"private": true` — marca el paquete como no publicable en el registro público de npm. Es una salvaguarda: evita subir por error código interno.
- `"type": "module"` — indica que los `.js`/`.ts` usan sintaxis de **ES Modules** (`import`/`export`) en lugar del antiguo CommonJS (`require`). Por eso el `playwright.config.ts` usa `import` y `export default`.
- **Scripts:**
  - `"test": "playwright test"` — ejecuta toda la batería de tests.
  - `"test:ui": "playwright test --ui"` — abre el modo interfaz gráfica de Playwright, útil para desarrollar/depurar tests viéndolos paso a paso.
  - `"codegen": "playwright codegen"` — lanza el grabador: interactúas con la web en un navegador y Playwright genera el código del test automáticamente.
  - `"typecheck": "tsc --noEmit"` — comprueba los tipos de TypeScript sin generar archivos de salida (`--noEmit` = "no emitas JS"). Solo valida que el código es correcto en tipos; encaja con la fase de `typecheck` del pipeline CI.
- **devDependencies** (dependencias solo de desarrollo, no de producción):
  - `"@playwright/test"` — el framework de testing de Playwright (el *test runner* con `test`, `expect`, etc.).
  - `"@types/node"` — las definiciones de tipos de TypeScript para la API de Node.js. Sin este paquete, TypeScript no conocería cosas como `process.env`, que sí se usa en la config. Por eso también aparece en el `tsconfig`.

---

### `e2e/tsconfig.json`

**1. Qué es.** El archivo de configuración de **TypeScript** para el paquete `e2e/`. Le dice al compilador `tsc` qué reglas aplicar y qué archivos vigilar.

**2. Para qué sirve.** Configura el chequeo de tipos de este paquete. Es lo que consulta el script `typecheck` (`tsc --noEmit`) y también lo que usa el editor para dar autocompletado y errores en rojo.

**3. El porqué de cada decisión:**
- `"extends": "../../tsconfig.base.json"` — hereda de un tsconfig **base** en la raíz del monorepo. Esta es una práctica clave en monorepos: las reglas comunes (strict mode, target de JS, etc.) se definen una sola vez en la raíz y cada paquete solo añade lo específico. Aquí el archivo es intencionadamente mínimo porque casi todo viene heredado.
- `"types": ["node"]` — limita qué paquetes de tipos globales se cargan automáticamente: solo los de Node. Esto es lo que habilita usar `process.env` sin errores de tipo. Restringir la lista evita cargar tipos globales innecesarios.
- `"include": ["tests", "playwright.config.ts"]` — le indica a TypeScript qué archivos analizar: la carpeta `tests` (donde están los `.spec.ts`) y el propio archivo de configuración de Playwright. Nada más entra en el chequeo de tipos.

---

### `e2e/playwright.config.ts`

**1. Qué es.** El archivo de configuración de **Playwright**, escrito en TypeScript. Usa el helper `defineConfig` (que aporta autocompletado y validación de tipos de las opciones) y exporta la config por defecto.

**2. Para qué sirve.** Define cómo se ejecutan los tests E2E: dónde están, contra qué URL apuntan, en qué navegadores corren y cómo se comporta todo distinto en local frente a CI.

**3. El porqué de cada decisión:**
- `const baseURL = process.env.E2E_BASE_URL ?? "http://localhost:5173"` — la URL base sale de una variable de entorno; si no está definida, usa por defecto `http://localhost:5173`, que es el puerto por defecto del servidor de desarrollo de **Vite** (el de `apps/web`). El operador `??` (*nullish coalescing*) toma el valor por defecto solo si la variable es `null`/`undefined`. Hacerlo configurable por entorno permite apuntar a otra URL en CI. El comentario del archivo lo aclara: "apuntará a apps/web cuando exista".
- `testDir: "./tests"` — carpeta donde Playwright busca los tests.
- `fullyParallel: true` — ejecuta todos los tests en paralelo para que la suite termine antes.
- `forbidOnly: !!process.env.CI` — si está en CI, prohíbe los `test.only` (que ejecutan un único test y silencian el resto). Evita que un `.only` olvidado se cuele y haga que el pipeline pase sin ejecutar la suite completa. El `!!` convierte la variable a booleano.
- `retries: process.env.CI ? 2 : 0` — en CI reintenta 2 veces los tests que fallan (para absorber fallos intermitentes/*flaky*); en local, 0 reintentos, para que veas los fallos de inmediato.
- `reporter: process.env.CI ? "github" : "list"` — en CI usa el reporter `"github"` (integra los errores con la interfaz de GitHub Actions); en local usa `"list"`, un resumen legible en consola.
- **`use`** (opciones aplicadas a todos los tests):
  - `baseURL` — así en los tests puedes escribir `page.goto("/")` en vez de la URL completa.
  - `trace: "on-first-retry"` — genera un *trace* (grabación detallada para depurar) solo la primera vez que un test se reintenta. Es un equilibrio: no gastas recursos grabando los tests que pasan, pero capturas información justo cuando algo falla.
- **`projects`** — define matrices de navegadores: `chromium` (con el perfil `Desktop Chrome`) y `firefox` (con `Desktop Firefox`). Cada test se ejecuta en ambos, para verificar compatibilidad multinavegador. Los `devices[...]` son presets de Playwright con viewport, user-agent, etc.
- El bloque **`webServer` comentado** — está intencionadamente desactivado. Cuando exista `apps/web`, al descomentarlo Playwright arrancaría solo el servidor web (`pnpm --filter @bukit/web dev`) antes de los tests y reutilizaría uno ya abierto en local (`reuseExistingServer: !process.env.CI`). Está comentado porque `apps/web` todavía no existe (es un placeholder).

---

### `e2e/tests/example.spec.ts`

**1. Qué es.** Un archivo de test de Playwright (`.spec.ts`). Importa `test` y `expect` del framework.

**2. Para qué sirve.** Es un **test de humo de ejemplo** (*smoke test*: la comprobación mínima de que lo básico funciona). Sirve de plantilla/semilla; su propio comentario dice que "se sustituirá por los flujos reales cuando exista apps/web".

**3. El porqué de cada decisión:**
- `test.skip("la home carga", ...)` — usa `.skip`, es decir, el test está **desactivado a propósito**. No se ejecuta todavía porque `apps/web` aún no existe y no habría nada que cargar; dejarlo con `.skip` evita que la suite falle mientras tanto, pero mantiene el código de ejemplo a la vista.
- `await page.goto("/")` — navega a la raíz; funciona con ruta relativa gracias al `baseURL` de la config.
- `await expect(page).toHaveTitle(/BUKIT/i)` — comprueba que el `<title>` de la página contiene "BUKIT". La `/BUKIT/i` es una expresión regular con la bandera `i` (*insensible a mayúsculas/minúsculas*), así que valida el título sin importar cómo esté capitalizado.

En resumen: es un stub funcional pero desactivado, pensado para reemplazarse por tests reales.

### `apps/web/README.md`

**1. Qué es.** El README (documentación en markdown) de la futura app web. **Es un placeholder**: no hay código de la app todavía, solo instrucciones de cómo crearla.

**2. Para qué sirve.** Documenta qué será `apps/web` (el **cliente para navegador: React + Vite + TypeScript**, con Redux Toolkit + Reselect y TanStack Query para el estado de servidor / feed infinito) y deja las instrucciones para generarla cuando llegue el momento.

**3. El porqué de cada decisión (según el propio texto):**
- Explica *por qué* aún no hay código: para "no escribir a mano una config de Vite que quedaría desactualizada". Es decir, se prefiere generar el scaffold con la herramienta oficial en lugar de teclearlo manualmente.
- El comando `pnpm create vite@latest web -- --template react-ts` usa la plantilla oficial `react-ts` (React con TypeScript). El `--` separa los flags que van dirigidos a la herramienta creada, no a `pnpm`.
- Pasos posteriores documentados: fijar `"name": "@bukit/web"` (integrarla en el scope del monorepo), y añadir las dependencias `"@bukit/core": "workspace:*"` y `"@bukit/ui-core": "workspace:*"`. La notación `workspace:*` es específica de pnpm en monorepos: significa "usa la versión de ese paquete que está aquí mismo en el repositorio", no una de npm. Y crear un tsconfig que extienda `../../tsconfig.base.json`, igual que hace el paquete `e2e/`.

### `apps/mobile/README.md`

**1. Qué es.** El README de la futura app móvil. También **es un placeholder**, sin código de app todavía.

**2. Para qué sirve.** Documenta que `apps/mobile` será la **app nativa iOS/Android: React Native + Expo + TypeScript** (con EAS build, actualizaciones OTA y notificaciones push), y da las instrucciones para generarla.

**3. El porqué de cada decisión (según el texto):**
- El comando `pnpm create expo-app@latest mobile` usa la herramienta oficial de Expo para crear el proyecto, siguiendo la misma filosofía que la web: scaffolding oficial en vez de config manual.
- Pasos posteriores: fijar `"name": "@bukit/mobile"` y añadir `"@bukit/core": "workspace:*"` y `"@bukit/ui-core": "workspace:*"` — exactamente los mismos paquetes compartidos que la web, lo que refleja el principio del monorepo de compartir lógica (tipos, validación, cliente API) entre web y móvil.
- La advertencia sobre **Metro y los symlinks de pnpm**: Metro es el *bundler* de React Native. pnpm instala dependencias usando enlaces simbólicos (symlinks), y Metro a veces no los resuelve bien. La solución documentada es descomentar `node-linker=hoisted` en el `.npmrc` de la raíz, que cambia cómo pnpm coloca los paquetes (los "eleva"/aplana en vez de usar symlinks), para que Metro los encuentre.
